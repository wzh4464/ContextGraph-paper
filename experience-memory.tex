\section{Problem and motivation}
\label{sec:motivation}
A coding agent receives an issue and a repository and produces a patch.
Its trajectory records actions, observations, and the outcome. ContextGraph
builds an experience graph $G$ from completed trajectories, retrieves guidance
for each new task, and updates $G$ afterward. The goal is to accumulate useful
repair experience across tasks and repositories.

\paragraph{A debugging decision that transfers.}
In Django Trac \#33018, empty query results are mishandled under negation.
A failed \texttt{python-statemachine} attempt had spent its effort setting
up a full Django application; its lesson was to isolate the failure before
investing in framework setup. A successful \texttt{sievelib} trajectory also
supported reproducing the failure before editing. Guided by these experiences,
the agent traced the fault to \texttt{Exists.as\_sql()}, corrected its
handling, and added a regression test. The no-memory attempt made broad
formatting changes without fixing the bug. The transferable content was the
investigation strategy and warning; the agent derived the local implementation.
Neither source repository is Django: the lesson crossed repositories, and
Section~\ref{sec:cross-repo} measures how often selected lessons do so.

\paragraph{From advice to applicable guidance.}
Figure~\ref{fig:concept} contrasts two memories for this case: a flat
summary store returns one requirement sentence, whereas the agent selects
from ContextGraph a strategy, a warning, and the condition under which they
apply, each linked to its source attempt. The condition tells the agent when
the lesson holds; the source lets it check how the lesson was applied before
adapting it to the current code.

\section{ContextGraph: memory for planning, recovery, and learning}
\label{sec:method}
ContextGraph connects experience abstraction, agent-directed selection, and memory
access. The same process builds the initial graph and incorporates completed
tasks (Figure~\ref{fig:experience-memory}).

\subsection{Experience abstraction: retain the useful decision}
\label{sec:experience-abstraction}
A language model extracts lessons from the task, actions, errors, and outcome.
Each lesson records a strategy or warning, its applicability conditions, the
outcome it is meant to achieve or preserve, and source context. For the
initial graph, abstraction removes repository-specific names while retaining
the decision and its reason: the failed framework setup becomes advice to
isolate the bug first. Lessons distilled online take the form ``when you see a
symptom, do an action so that a result follows'' and keep the files and
commands the agent used, so later tasks in the same repository can reuse
them.

We represent memory as a typed graph
\begin{equation}
 G=(V,E),\qquad E\subseteq V\times\mathcal R\times V,
 \label{eq:experience-graph}
\end{equation}
where each edge has a relation type in $\mathcal R$. Nodes represent
trajectories, fragments (action--observation segments), strategies (extracted
lessons, including warnings), canonical rules (merged lessons), error patterns, problem summaries, playbook entries
(retrieval-ready lessons), and communities of related fragments. The seven
edge types connect a trajectory to its fragments, a strategy to its source
trajectory, a fragment to an encountered error, a strategy to its canonical
rule, a rule to an error it addresses, a summary to its trajectory, and a
fragment to its community. These links retain both a reusable lesson and the
observations that explain when it applies. Appendix~\ref{sec:historical}
lists the node and edge counts of a graph snapshot, and the anonymous repository
(Section~\ref{sec:setup}) releases the extraction prompts, schema, and
selection code.

\subsection{Agent-directed selection: find useful experience}
\label{sec:experience-retrieval}
At repair step $t$, the agent uses its full context $C_t$: the issue, inspected
code, actions, and failures. Memory selection is an agent decision process:
\begin{equation}
 a_j\sim\pi_\theta(\,\cdot\mid C_t,H_j),\qquad
 \mathcal M_t=\operatorname{Select}_{\pi_\theta}(C_t,G_t),
 \label{eq:agent-selection}
\end{equation}
where $\pi_\theta$ is the coding agent's model policy, $H_j$ records its
preceding memory actions and their results, and $\mathcal M_t$ contains the
selected lessons. Actions search the entire pool, read source records, follow
graph links, select lessons, or stop. Searches return ranked candidates; the
agent matches each candidate's applicability conditions against its current
task and error and decides which lessons to keep, so the number of selected
lessons varies by task. It applies the selected guidance through local reproductions, edits,
and tests (Appendix~\ref{sec:agentic-retrieval}).

\subsection{Memory access and updates: connect repair to learning}
\label{sec:experience-access}
Memory enters the repair loop at three points.
\textbf{Before planning,} the agent searches with the full task context for
investigation, reproduction, and testing strategies, and for warnings about
costly approaches to avoid.
\textbf{After an error,} it adds the failed action, observed error, relevant
code, and current hypothesis to that context, searches again to revise its
diagnosis, and uses repository tools to try the next step.
\textbf{After each task,} ContextGraph distills successful and failed trajectories and links new
lessons to existing experience. Updates use agent-visible observations and
become immediately available to later tasks (Appendix Algorithm~\ref{alg:contextgraph}).
Because memory grows during evaluation, a task late in the stream selects
from a larger graph than an early one, and a retry of an unresolved task can
select the lessons distilled from its own earlier failure
(Section~\ref{sec:stream}).
