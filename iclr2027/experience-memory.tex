\section{Problem and motivation}
\label{sec:motivation}
A coding agent receives an issue and a repository, investigates the failure,
and produces a patch. Its trajectory records the task, actions, observations,
and outcome. ContextGraph uses completed trajectories to build an experience
graph $G$. For each new task, the graph supplies guidance for the agent's
current decision; after the task, the trajectory updates $G$ for later tasks.
The goal is to make repair experience accumulate across tasks and repositories.

\paragraph{A debugging decision that transfers.}
In Django Trac \#33018, empty query results are mishandled under negation.
A failed \texttt{python-statemachine} attempt had spent its effort setting
up a full Django application; its lesson was to isolate the failure before
investing in framework setup. A successful \texttt{sievelib} trajectory also
supported reproducing the failure before editing. Guided by these experiences,
the agent traced the exception to \texttt{Exists.as\_sql()}, corrected its
handling, and added a regression test. The no-memory attempt made broad
formatting changes without fixing the bug. The transferable content was the
investigation strategy and warning; the agent derived the local implementation.

\section{ContextGraph: memory for planning, recovery, and learning}
\label{sec:method}
ContextGraph connects experience abstraction, graph retrieval, and memory
access during repair. The same abstraction process builds the initial graph
and incorporates every completed task, creating the learning loop in
Figure~\ref{fig:experience-memory}.

\subsection{Experience abstraction: retain the useful decision}
\label{sec:experience-abstraction}
From a trajectory's task description, actions, errors, and outcome, a language
model extracts lessons about debugging, testing, navigation, and failed
approaches. Each lesson records an action or warning, the situation in which
it applies, and its source context. Abstraction removes repository-specific
names while retaining the decision and its reason: the failed framework setup
in our example becomes advice to isolate the bug first.

The graph organizes these lessons around experiences, strategies, shared
rules, and error patterns. A strategy links back to its source trajectory;
similar strategies connect to a shared rule; rules and experiences connect
to the errors they address or encounter. This structure preserves both the
common lesson and the observations behind it. A warning from a failed attempt
can therefore remain useful alongside a strategy from a successful repair.

\subsection{Graph retrieval: find relevant strategies and warnings}
\label{sec:experience-retrieval}
A query describes the task and the agent's current situation. Semantic search
finds lessons with related meaning, while keyword search matches diagnostic
terms. A graph walk follows links from error patterns through shared rules
and source strategies to past trajectories. Different errors can thus lead
to a common debugging strategy. The retriever merges candidates from these
channels and selects a small, diverse set of lessons.

The returned memory contains actions, warnings, applicability context, and
source experience. The agent interprets them against the current code and
constructs its own reproduction, patch, and tests. Figure~\ref{fig:experience-memory}
illustrates why this organization is useful: both a setup failure and an
incorrect output can point to the strategy of isolating the failing behavior.
Appendix~\ref{sec:agentic-retrieval} describes full-context agent search as a
further extension of this retrieval interface.

\subsection{Memory access and updates: connect repair to learning}
\label{sec:experience-access}
\paragraph{Before planning.}
The agent queries the graph with the issue and available code context.
Strategies guide where to investigate, how to reproduce the failure, and
which checks to prioritize; warnings identify costly approaches to avoid.

\paragraph{After an error.}
A failed command, reproduction, or test supplies a more specific query:
the observed error, recent action, relevant files, and current hypothesis.
Retrieval now supports diagnosis and revision. The agent applies the guidance
through its repository tools and uses the next observation to decide how to proceed.

\paragraph{After each task.}
ContextGraph applies the abstraction process to the completed trajectory,
including both successful and failed attempts. It adds the resulting lessons,
links them to source context and existing experience, and updates their
retrieval entries. New experience is immediately available to subsequent
tasks. The two within-task query points help the current repair; the update
step turns that repair into memory for the next task.
Algorithm~\ref{alg:contextgraph} summarizes the complete workflow.

\begin{algorithm}[!htbp]
\caption{ContextGraph across a stream of coding tasks}
\label{alg:contextgraph}
\small
\begin{tabular}{@{}p{0.96\linewidth}@{}}
\textbf{Input:} initial trajectories $H$, coding tasks $q_1,\ldots,q_T$.\\
\textbf{Output:} candidate patches and an updated experience graph $G$.\\
1. Extract strategies and warnings from $H$; build $G$ and its retrieval entries.\\
2. \textbf{For each} task $q_t$:\\
\quad a. Query $G$ with the issue and code context; use the guidance to form a plan.\\
\quad b. Execute investigation, editing, and testing actions; record the trajectory.\\
\quad c. After an error, query $G$ with the failure and recent action; revise the plan.\\
\quad d. Continue the repair loop until the task ends or its budget is exhausted.\\
\quad e. Distill the successful or failed trajectory into new experience.\\
\quad f. Update $G$ and retrieval entries; expose the new experience to later tasks.\\
\end{tabular}
\end{algorithm}
