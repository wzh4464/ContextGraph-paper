\begin{abstract}
A past repair is useful only under the conditions that made it work.
We investigate how coding agents can use past repairs to choose informative observations of the current program.
Our motivating experiments on 99 SWEContextBench Related-Lite tasks find 17 resolved tasks without memory, 18 with flat patch retrieval, and 18 with an added repository procedure card.
A two-task training pilot obtains the same successful patches with the applicability instruction both with and without memory.
The pilot's repairs therefore do not require historical content.
The resulting method represents a past repair by an executable check of its observable effect, confirmed by running the source before and after the repair.
We are testing whether this representation helps a new repair more than the original patch.
\end{abstract}

\section{Introduction}
Software repairs encode conditional knowledge.
Adding a conversion, changing an ordering constraint, or copying an object can fix a bug because a particular input, runtime, and program state make that change necessary.
Removing those conditions turns a useful experience into advice that may point in the wrong direction.
Two issues can mention the same API and exception while requiring different edits.
A memory that says what worked previously still leaves the agent to determine what is true now.

Our starting point is to ask what observation would make a past experience useful for the next repair decision.
Does comparing the behavior before and after a source repair identify what is worth measuring in a new task?
We study a memory representation that records this behavioral contrast, with verified target repairs as the measure of its value.

\section{Why relevant experience can be insufficient}
\label{sec:motivation}
\paragraph{More guidance did not produce a clear gain.}
Our completed exploratory Related-Lite experiment compares six memory interfaces on the same 99 tasks from SWEContextBench \citep{swecontext2026}.
The solver is SWE-agent 1.1.0 with a DeepSeek V4 Pro model alias, temperature zero, a 500-call limit, and a history processor retaining the last five observations.
Flat retrieves historical patches; Card adds a repository procedure card; Graph, Rules, and File list expose other representations of the available experience.
Related source fixes can closely match target repairs.

Flat and Card each gain one observed repair over no memory; both exact paired tests give $p=1$, providing no demonstrated gain in this setting.

Patch memory reaches all 99 targets in both conditions, and the expected procedure card reaches 98.
However, reconstructing 198 Flat/Card histories shows that an original memory response is retained for a median of only five action prefixes.
The median trajectories contain 497 and 495 actions, respectively.
The development pilot below keeps memory persistent to remove this delivery constraint.

\paragraph{The same operation can be a repair or a bug.}
A Requests training example makes the applicability problem concrete.
Issue 1724's patch adds \texttt{method = builtin\_str(method)} to normalize an HTTP method in a Python 2 setting.
Issue 2317 instead reports that this conversion turns Python 3 bytes \texttt{b'GET'} into the literal string \texttt{"b'GET'"}.
Its training patch uses \texttt{to\_native\_string(method)}.
A retrieved recommendation to perform the older conversion is related to the target but does not settle the correct action.

Here the issue already states the relevant input and runtime; rerunning that example would confirm known information.
The useful check would instead distinguish actions whose applicability remains uncertain after reading the issue.

\section{The applicability pilot succeeds without memory}
\label{sec:experiments}
The completed pilot uses Requests 1921 and pytest 10051 from the training pool of our separate SWE-bench Verified split \citep{swebench2024}.
The split allocates 350 tasks to memory construction and development and 150 to evaluation, with repository-stratified allocation and seed 42.
The two pilot tasks belong to a 70-task development partition whose source rules are excluded from the remaining 280-source memory bank; the 150 evaluation tasks are unused here.

The two memory conditions receive the same persistent packet from \cg{}'s dense, lexical, and graph retrieval pipeline.
One uses the ordinary solver; the other adds an instruction to state an applicability condition, execute at most two short checks before editing, and use their observations to accept or reject a recommendation.
The instruction does not enforce these decisions.
We hold the model, tools, task images, \$3 metered threshold, and 100-call limit fixed, and grade each submitted patch immediately with the Verified harness.

Ordinary memory produces two empty patches after 39 and 49 calls.
Adding the instruction produces two verified repairs after 36 and 17 calls.
Removing only the memory packet also produces two verified repairs, after 30 and 34 calls; both patches are identical to their counterparts with memory.
The ordinary runs never edit source, whereas both instruction conditions do.
This two-task result shows that the observed repairs can occur without historical content.
It directs method development toward the information supplied by experience, rather than expanding the instruction-only prototype.

\section{Remembering a repair's observable effect}
\label{sec:method}
A check that passes on a repaired program may describe a general property without exposing anything learned from the repair.
In a source-side trial on Matplotlib 23314, four checks generated from fixed code all pass before and after the repair: they exercise initialization, axis limits, sharing, and drawing order while missing the repaired visibility behavior.
Source repair sensitivity cannot select an informative check from this pool.

Our revised construction gives the memory writer the source patch and fixed implementation and asks for a check of the changed observable behavior.
It executes the check on the buggy and repaired source with two legal inputs.
An admitted check must run normally in both versions and expose a false-to-true relation; execution errors return to the writer for program correction.
The stored memory contains the source issue, relation, and executable check.

The observable effect matters because a repair can also change incidental internal state.
A generated check of Matplotlib's projection cache detects the source change, but the corresponding cache does not exist in the two-dimensional target API.
Changing both the operation and the measured state would invent a different check.
We therefore require observations of rendered output or documented API results, rather than an implementation-specific cache.
A generated output check renders a hidden blue axes region on a red figure.
Before the source repair, the two inputs leave 57,600 and 40,000 non-red pixels; after the repair, both leave zero.
The writer corrected an invalid API call using its execution error before this contrast was measured.

The target solver binds the check's objects and API calls to the current repository while retaining the operation sequence and measured relation.
The current issue determines whether that relation should hold in the target.
The intended benefit is an observation that changes a repair decision enough to repay the cost of adaptation and execution.
The development comparison supplies either the original source patch, the constructed effect check, or no memory to the same target solver at the same budget.
Target transfer remains under evaluation.

\section{Related work}
\paragraph{Experience and skills.}
ExpeL distills reusable insights from agent trajectories \citep{expel2024}.
SWE-Exp uses historical experience for software issue resolution \citep{sweexp2025}, and MemGovern turns human experience into searchable cards \citep{memgovern2026}.
CODESKILL learns a skill extraction and maintenance policy using feedback from a frozen downstream solver \citep{codeskill2026}.
ExpeRepair retrieves historical test demonstrations and reflective insights to generate reproduction and boundary tests \citep{experepair2026}.

\paragraph{Repair patterns and context.}
Getafix learns fix patterns from human patches and uses surrounding code to rank applicable edits \citep{getafix2019}.
VulDebugger compares expected constraints with observed runtime state to guide vulnerability repair \citep{vuldebugger2025}.
MemRepair combines historical fixes, security patterns, and refinement trajectories with runtime feedback \citep{memrepair2026}.
MR-Scout parameterizes relations from existing tests, and MR-Coupler generates relation tests from coupled methods and evaluates historical defects \citep{mrscout2023,mrcoupler2026}.
The question here is whether a source repair's behavioral change improves the selection of a check for a different repair task.

\paragraph{Graph retrieval and working memory.}
HippoRAG motivates associative retrieval with Personalized PageRank \citep{hipporag2024}.
SWE-MeM studies working-memory management \citep{swemem2026}, while cue-anchored memory studies delivery through coding-task and compaction experiments \citep{cueanchored2026}.
AdaMEM retrieves experience at intermediate states and synthesizes an updated strategy \citep{adamem2026}.
Decision-Aware Memory Cards scores context by estimated effects on actions \citep{cicl2026}.
