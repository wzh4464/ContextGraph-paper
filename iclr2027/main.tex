\begin{abstract}
Past repairs record requirements that a new issue may leave unstated.
We study candidate-conditioned repair memory: execute a historical behavioral condition on an initial repair, and use a remaining violation to guide a revision that preserves the current fix.
The key decision is whether the candidate still needs the experience.
On a Django development task, an initial repair and an additional issue-based review both pass official verification but discard query parameters during redirection.
Historical information enables a revision that preserves both the required deployment prefix and the omitted query parameters, including a joint input withheld from the writers.
The historical patch and executed source check yield the same revision; when ordinary candidates already satisfy a source condition, the procedure requests no correction.
\end{abstract}

\section{Introduction}
The issue description tells a coding agent what is currently reported as broken.
It need not enumerate every behavior a complete repair should preserve.
A retrieved experience is useful when it supplies a missing requirement that changes the candidate repair.
Similarity to the issue, or a new observation about the program, is insufficient if the candidate already handles that condition.

Consider an administrative redirect that must preserve a deployment prefix.
Changing its destination from \texttt{request.path\_info} to \texttt{request.path} fixes that reported fault.
However, appending a slash to the resulting path still discards query parameters.
A different repair of the same API records this omitted behavior and replaces path concatenation with \texttt{request.get\_full\_path(force\_append\_slash=True)}.

We investigate a procedure organized around this residual defect.
First construct a candidate from the current issue.
Then assess a relevant historical condition on the patched program and revise when that condition exposes an omission compatible with the current task.
This makes the proposed repair, rather than issue relevance alone, the object of the memory decision.
Our development evidence distinguishes this useful omission from a historical condition already covered by ordinary repairs.

\section{Memory conditioned on the candidate repair}
\label{sec:method}

\paragraph{Recover the historical requirement.}
A source record contains a buggy program, its repair, and the repaired program.
A writer receives the patch and relevant repaired code and generates a short executable check of the repair's observable effect.
We execute it in both source versions.
The check must run normally, hold after the repair on the supplied legal inputs, and change from false to true on at least one input.
The resulting memory records the relation and the behavior demonstrating its relevance to the source repair.

\paragraph{Look for a remaining violation.}
Let $p$ be the initial candidate for target program $T$, and let $r$ be a source relation that can be instantiated on that target.
We evaluate $r$ on $T\oplus p$, the program after applying the candidate.
In the experiments below, we select a source repair of the same API and execute its generated check unchanged on the target candidate.
A normal execution with a false result identifies a possible omission; a true result means that this relation provides no reason to revise the candidate.
The target's required behavior determines whether the source condition is relevant.
Execution errors provide neither observation.

This distinction matters when every candidate receives the same source-check result.
If all satisfy the relation, it supplies no selection value.
If all violate a relevant relation, ranking the same candidates cannot recover the missing behavior; the useful operation is to generate a corrective edit.
The procedure therefore uses a violated source condition to request a revision and instructs the writer to preserve the behavior the initial candidate already fixes.

\paragraph{Revise using the experience.}
The revision writer receives the issue, initial implementation, candidate, and observations of the reported fault after the candidate is applied.
Historical information can be supplied as the source issue and patch, or as the source relation, its before/after observations, and the check's observed failure on the candidate.
The writer makes one revision call and returns a complete revised method.
Each resulting patch is immediately evaluated by the official SWE-bench verifier \citep{swebench2024}; the behavioral checks then measure whether the reported requirement and historical condition hold together.
The experiment supplies a selected source repair so that this comparison isolates its contribution to revision.

\section{Evidence: recovering an omitted requirement}
\label{sec:evidence}
We use the training side of a SWE-bench Verified split with 280 source tasks, 70 development tasks, and a separate 150-task evaluation partition unused by these experiments.
The principal pair is source Django 16612 and development target Django 14404.
The target issue asks for support of \texttt{FORCE\_SCRIPT\_NAME} in administrative redirects.
The source condition concerns query preservation in the same method.

\paragraph{An ordinary repair leaves the historical fault.}
DeepSeek V4 Pro generates one initial repair from the issue and relevant initial code, including the available request-path APIs.
The writer may replace \texttt{AdminSite.catch\_all\_view()} while preserving its signature and decorator.
Its repair keeps URL resolution based on \texttt{path\_info} and constructs the redirect from \texttt{request.path}.
Official verification passes, and an issue-based check confirms that the deployment prefix is retained.
The unchanged source program executes normally on this candidate and observes that both query strings are discarded.

\paragraph{Memory changes the revision.}
Starting from that same candidate, three independent revision calls receive either the issue-based evidence alone, the historical issue and patch, or the executed source relation.
All use the same model, temperature 0.7, and one call with a 16,384-token output allowance.
The issue-based review retains the initial patch.
Both memory conditions replace path concatenation with \texttt{get\_full\_path(force\_append\_slash=True)}, producing byte-identical patches.
Those revisions retain the deployment prefix and preserve the query parameters (Table~\ref{tab:residual}).

\paragraph{The revision preserves the requirements together.}
An independently prepared joint check combines the deployment prefix with repeated query parameters and percent-encoded values:
\texttt{keep=a\%2Fb\&keep=c\%20d}.
This input is withheld from all writers and executed after their revisions and official verifications complete.
Both memory revisions preserve the exact prefix and query string in the redirect; the initial and issue-reviewed candidates lose the query string.

\paragraph{A covered condition contributes no corrective signal.}
Source Django 16493 records that serializing a \texttt{FileField} should preserve its original storage factory even when the factory returns \texttt{default\_storage}.
On development target Django 13343, four independent source-blind candidates produce the same AST repair and all satisfy that relation.
Each also passes official verification.
The source condition therefore supplies no additional candidate-selection value in that pool.


\section{Related work}
ExpeL distills reusable insights from experience, and Getafix learns applicable edit patterns from human repairs \citep{expel2024,getafix2019}.
ExpeRepair uses historical test demonstrations and reflective insights to generate reproduction and boundary tests \citep{experepair2026}.
MIRA constructs repair memory from SQL corrections and uses database evidence to activate and combine applicable repair units \citep{mira2026}.
These works already establish repair reuse, historical test guidance, and execution-based memory activation.
Our empirical focus is the residual requirement: whether historical information changes a candidate that already fixes the reported fault, and whether the resulting revision preserves the old and new requirements together.
