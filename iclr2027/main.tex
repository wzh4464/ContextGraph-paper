\begin{abstract}
A coding agent can fix the reported bug while missing a requirement already
learned in an earlier repair. ContextGraph turns this experience into reusable
repair memory: a requirement, the input that triggers it, and an executable
observation of the desired behavior. FAISS selects candidate experiences;
graph relations connect their inputs and operations so that historical
conditions can be composed with the current workflow.
Earlier ContextGraph retrieval experiments show the value of experience:
on SWEContextBench Related-Lite, curated memory raises first-pass resolution
from 14/99 to 21/99 and reaches 25 resolved tasks in two passes, which the
no-memory agent reaches in three.
Our executable-memory development experiments explain how history improves
the repair itself. In three paired Django cases, memory adds query preservation,
constraint handling, or destination-timezone behavior beyond the reported bug.
A further comparison shows that composing a historical input with the current
query recovers a behavior that checking the two separately misses.
The central idea is to retrieve a condition the next repair should satisfy,
and make that condition available to execution and refinement.
\end{abstract}

\section{Introduction}
Coding agents repeatedly encounter related bugs, yet each new issue describes
only part of what a complete repair should accomplish. Past fixes contain
knowledge that the new issue leaves implicit: which argument takes precedence,
which constructor convention matters, and which neighboring operation must
continue to work. Long-term memory offers a way to carry these requirements
from one repair to the next.

Consider an administrative redirect that loses a deployment prefix. An agent
can repair the prefix by using the full request path, yet still discard query
parameters when appending a slash. A historical fix of the same API records
the missing requirement: retain the query string. The history-informed agent
uses \texttt{get\_full\_path()} with slash appending enabled, preserving both
the prefix and the query. Memory contributes a behavior that the current issue
did not ask the agent to rediscover.

This example suggests a useful unit of experience: a requirement together with
the conditions that make it matter. A patch shows one implementation of that
requirement. A sentence makes it portable. An executable witness supplies the
input and observation needed to apply it accurately. ContextGraph combines
these forms by storing the requirement with its triggering input and observed
operation, then composing those relations with the current program.

Our investigation follows three questions: \emph{which memory is useful, how
should it be represented, and how should it be retrieved?} Historical benchmark
results establish where experience helps: earlier ContextGraph systems improve
single-pass resolution across several backbones and reach useful solutions
with fewer retry rounds. Development interventions then identify the information
responsible for a better repair. This leads to a graph whose role goes beyond
ranking similar text: it supplies the relations needed to construct a relevant
check from the retrieved experience.

We contribute an executable requirement representation; a retrieval interface
combining FAISS candidates with graph-based input and operation composition;
and empirical evidence connecting memory content to both task resolution and
the behaviors preserved by the resulting repair. The resulting design principle
is simple: \emph{remember what a repair must accomplish, and retain enough of
its conditions to exercise that requirement in the next task.}

\section{ContextGraph: memory as executable requirements}
\label{sec:method}
\subsection{Represent the behavior learned from a repair}
For a historical repair, let $V^{-}$ and $V^{+}$ be the original and repaired
versions. We store
\begin{equation}
 m=(r,W,E^{-},E^{+}),\qquad W=(I,A,O),
 \label{eq:witness}
\end{equation}
where $r$ states a requirement, $I$ constructs an input, $A$ performs the
operation, and $O$ observes whether its outcome meets $r$. The two executions
$E^{-}$ and $E^{+}$ apply the same witness to the source versions. A false-to-true
change identifies a behavior learned from the repair. Neighboring inputs that
pass on both versions describe behavior to preserve around that trigger.

A source writer receives the historical issue, patch, and relevant code, then
constructs the requirement and witness. Separating input, operation, and
observer makes the experience reusable. The agent can locate a new
implementation of $r$ while retaining the input condition that justified it.
For example, named tuples and ordinary tuple subclasses can hold the same
values but require different constructor calls. Their type relation is part
of the requirement's usable context.

\subsection{Retrieve candidates, then recover their relations}
The graph links a historical repair to its requirement, witness, and executions.
Execution edges identify the functions reached by the witness. Input edges
bind a constructor and its values to an argument of the observed operation.
These relations let the retriever return a complete condition and let a
composition operator determine which construction to carry into a new program.

A reader uses the public issue and original repository to identify the current
operation. Qwen3-Embedding-8B/FAISS similarity selects historical sources from
the same repository \citep{qwen3embedding2025}. The current implementation keeps
the top three distinct witnessed sources. Graph joins then return their
requirements, complete programs, observations, and input relations.
Operation connections accompany these candidates: a repair may need to preserve
behavior outside the initially localized function, so an early function match
does not veto a high-ranked source.

For range queries, assignment and branch analysis identifies the named-tuple
constructor actually supplied to \texttt{filter(value\_\_range=bounds)}.
For timezone witnesses, the graph binds the stored instant and active timezone
to the explicit \texttt{tzinfo} arguments of observed
\texttt{TruncDate}/\texttt{TruncTime} calls. The relation retains both a value
and its role, allowing later checks to combine database, ambient, and
destination timezones correctly.

\subsection{Compose history with the current workflow}
A historical example and a current example may each pass while their
combination fails. We therefore compose the historical input condition along
the current operation. Our ORM adapter lifts a scalar lookup
\texttt{field=x} into a point-range lookup
\texttt{field\_\_range=R(x,x)}, using the historical two-endpoint named tuple
\texttt{R}. Writing the public example as $P_q(x)$ gives
\begin{equation}
 P_q(x)\longmapsto P_q^{\mathrm{range}}(R(x,x)).
 \label{eq:composition}
\end{equation}
The adapter retains the construction of $x$ and the surrounding query. An
ordinary-tuple point range supplies a neighboring check. When $x$ is a lazy
User inside an annotated subquery, retaining that object and operation sequence
is essential: a lazy integer or a standalone named-tuple query exercises a
different interaction.

The implementation transforms the public program's syntax tree using the
retrieved input relation. Each adapter specifies the operation it supports.
The composed program retains an explicit observer: an empty fixture can test
query acceptance, while a nonempty fixture tests the selected rows. This
makes both preparation and semantic omissions available to the agent.

\subsection{Use the condition during repair}
A complete SWE-agent receives the issue and memory, then browses, edits, runs
tools, and submits a patch. Memory can supply a requirement sentence, historical
implementation, or executable witness. When a witness fails on the current
candidate, the interface returns its unchanged program and failed observations
for refinement. A callable tool executes the supplied conditions on the working
tree, keeping their inputs and observers consistent across edits.

We immediately grade submitted repairs with the benchmark's official verifier
and execute historical, current, and joint requirements on the repair.
Joint checks measure the additional behavior supplied by memory; neighboring
checks measure the behavior preserved while adding it. Fixture failures are
recorded separately from observed violations of the checked requirement.
This interface connects three stages: selecting an experience, exercising its
condition, and incorporating that behavior into the submitted implementation.

\section{Experience improves resolution and reduces retry rounds}
\label{sec:benchmark}
\paragraph{Experimental setting.}
We report two stages of ContextGraph. The historical retrieval systems store
rules or repair episodes and expose them through a memory tool. Their results
on SWE-bench Verified and SWEContextBench \citep{swebench2024,swecontext2026}
are restored from the project's recorded experiment tables. The executable
requirement method in Section~\ref{sec:method} is evaluated through the development
interventions in Sections~\ref{sec:evidence}--\ref{sec:composition-results}.
The historical tables retain their original task sets, backbones, and attempt
regimes; they measure those earlier systems. Appendix~\ref{sec:historical}
collects the remaining tables and protocol details.

\paragraph{Useful experience transfers across backbones.}
Table~\ref{tab:swectx-crossmodel} compares six memory conditions on the historical
Related-Lite98 single-shot protocol. ContextGraph has the highest resolution
rate among the learned retrieval conditions on all four backbones. With GPT-5.4,
it resolves 34/98 tasks against 21/98 without memory; with Kimi K2.6, it resolves
28/98 against 18/97. The oracle-summary condition supplies the benchmark's
paired experience directly. ContextGraph's 34/98 on GPT-5.4 is close to its
35/98, showing the value of finding useful experience without being given that
pairing at query time.

\paragraph{Memory gets to useful solutions earlier.}
A separate Related-Lite99 campaign uses DeepSeek V4 Pro with a 500-call and
\$30 per-task budget in both arms. Its curated episodic memory retrieves
reference fixes, verification hints, and pre-base repository history at two
moments: before choosing an approach and after an error. The served pool
contains 291 static episodes. Each later pass retries only that arm's unresolved
tasks. Table~\ref{tab:swectx-stream} shows the practical benefit: memory reaches
25 resolved tasks after two passes, while the control reaches 25 after three.
The first two passes add seven and nine resolutions respectively, with no
control-only successes. By the third pass the gap narrows to two tasks.
This pattern locates the strongest observed advantage in earlier successful
repair. Excluding ten targets with near-duplicate source fixes retains a
first-pass gain of 19/89 versus 13/89 ($p=.031$). A separate replication across three additional backbones also raises
first-pass resolution (Appendix Table~\ref{tab:swectx-xmodel}).

\section{History supplies a missing repair requirement}
\label{sec:evidence}
The executable-memory experiments use a Verified split of 280 source tasks,
70 development tasks, and 150 held-out evaluation tasks. The cases below are
development interventions with DeepSeek V4 Pro through OpenRouter,
temperature zero and matched budgets within each comparison. They measure
whether history adds a required behavior to the submitted repair.
Table~\ref{tab:historicalrequirements} presents three such additions.
Django14404 uses the first-ranked source issue and patch; Django12708 and
Django11138 come from a fixed six-task cohort receiving three unchanged Flat
rules per task. Both arms pass official verification on all six cohort tasks.
The historical requirements distinguish the completeness of those repairs.

\paragraph{An omitted behavior of the same API.}
Django14404 reports that administrative redirects lose a deployment prefix.
Both agents fix the prefix and pass official verification, but only the repair informed by source16612 also preserves the query string.
A joint input combines the prefix with repeated and percent-encoded query values, \texttt{keep=a\%2Fb}\allowbreak\texttt{\&keep=c\%20d}.
Only the history-informed repair preserves both.

\paragraph{A neighboring operation.}
Django12708 reports ambiguous deletion of an ordinary index when a unique constraint uses the same columns.
The first retrieved source, 15732, instead concerns deletion of a unique constraint sharing its column with a primary key.
Both repairs fix ordinary-index selection; only the memory-informed repair also excludes primary keys when deleting unique constraints.
The source-generated PostgreSQL check runs unchanged on both target repairs.
A separate combined input creates an ordinary index, redundant uniqueness, and a primary key on the same column.
Both repairs preserve ordinary-index deletion, but only the memory-informed repair also deletes redundant uniqueness while retaining the primary key and data.
History supplies a requirement for the neighboring operation.

\paragraph{An independent argument of the same operation.}
Django11138 requires date conversions to respect the database's source timezone.
Source13363 requires \texttt{TruncDate} and \texttt{TruncTime} to honor an expression's explicit destination timezone.
Both agents repair the source timezone, but only the memory-informed repair also honors the destination.
A source-generated check distinguishes the historical versions and runs unchanged on the target repairs.
On an independent SQLite input combining a UTC+1 database with an explicit New York destination, only the memory-informed repair returns the correct date and time.
The issue and history constrain different ends of the conversion.

\paragraph{The addition can guide further repair.}
Two fresh agents start from the same completed ordinary timezone patch.
Issue-based additional review returns it unchanged; supplying a generated historical check and its failed observations leads the other agent to use \texttt{self.get\_tzname()} in both truncation methods.
Both revisions pass official verification, but only the latter passes the historical and joint inputs.
The intervention supplies corrective information that further issue-based review does not recover in this comparison.

\section{What information makes memory usable?}
\label{sec:content}

\paragraph{A requirement can suffice without the source implementation.}
On the redirect task, replacing the first entry of the existing Flat packet with its original issue and patch yields a byte-identical repair; both forms preserve the joint behavior.
Two new agents then revise the completed ordinary patch.
Both receive the source-generated sentence, ``The redirect location from AdminSite.catch\_all\_view includes the original query string.''
One also receives the generated check and its failed observations.
Both submit byte-identical repairs that pass official and joint checks.
The sentence-only agent finds \texttt{get\_full\_path()} in the current repository: memory communicates the desired behavior while the agent locates its implementation.
Here the portable requirement is enough for the agent to find and use the right implementation.

\paragraph{Which information makes the requirement usable?}
We select the constraint and timezone benefit cases and run four fresh complete agents per task, fixing the single historical source and its delivery before editing.
Two source-only constructions produce a behavioral requirement and an implementation reference; the combined input concatenates them unchanged.
All eight repairs pass official verification (Table~\ref{tab:memorycontent}).
On Django12708, only Implementation and Both also remove redundant uniqueness while preserving the primary key.
The Requirement agent tests a field with \texttt{unique=True}, but places \texttt{unique\_together} on a different, two-column set.
This nearby passing test loses the same-column condition stated in memory.
On Django11138, all three memory inputs preserve the explicit destination timezone, while the fresh no-memory repair omits it.
The Requirement agent finds \texttt{self.get\_tzname()} in the target implementation without being given that helper in memory.

The timezone repairs also differ on further conditions.

\paragraph{Execution feedback makes an omitted condition concrete.}
Two fresh agents refine the same original failed Requirement candidate, both receiving its requirement again.
One also receives the unchanged source-generated check and its actual failures for a field with a primary key or \texttt{unique=True}.
Requirement-only review excludes the primary key but still fails the ordinary unique-field condition.
Feedback adds generated-name disambiguation and passes both conditions.
Both revisions pass official verification and the withheld joint sequence.
The added behavior is recovery of the ordinary unique-field condition identified by feedback.

\section{Graph composition makes experience actionable}
\label{sec:composition-results}
\paragraph{Preserve the input relation, not just its values.}
On Django12663, both a three-source code-connected packet and a ten-source
similarity packet contain the historical named-tuple repair, source13590,
yet neither initial repair recovers its behavior. Three fresh revisions start
from the same candidate and source (Figure~\ref{fig:memory-content-scope}).
Original history and execution feedback recover named tuples; the requirement
sentence alone does not. The feedback repair expands every non-builtin
sequence into positional arguments, which also breaks ordinary tuple and list
subclasses. Original history retains the constructor distinction and passes
all displayed behaviors. This is precisely the relation the graph should carry:
the argument convention of the input's type, alongside its endpoint values.

\paragraph{Join the historical input to the current operation.}
The current issue involves a lazy User in a nested query; history contributes
a named-tuple range. On an earlier partial repair, the current scalar query and
the historical range query each pass, while a query combining them fails.
The composed condition reveals an omission in the second container
reconstruction. Four fresh refinements of that candidate illustrate its use:
history alone yields one of two repairs passing all seven measured conditions;
adding the constructed joint program and its failed observation yields two of
two. All four pass official verification. Both augmented agents execute the
joint input and repair the second reconstruction.

The deterministic adapter in Equation~\ref{eq:composition} reaches the same
omission while retaining the public program's lazy User and nested annotation.
It produces a named-tuple point range and an ordinary-tuple neighbor.
This is the graph's constructive contribution: an input relation from a past
repair becomes a concrete check along the current query.

\paragraph{A matched comparison isolates the added condition.}
A new original-base pair receives identical history, public scalar program,
its observed failure, a callable execution tool, and instructions to run the
supplied conditions before editing and submission. The augmented arm also
receives the two composed programs and their failures.
Both repairs pass official verification (Table~\ref{tab:composedconditions}).
The current-feedback repair fails both historical examples and the withheld
named-tuple/lazy-User query; the augmented repair passes those behaviors and
preserves the ordinary subclasses.
The augmented agent runs the joint input before editing and again after
removing a global conversion that broke an existing test. Its remaining
range-endpoint failure directs the final correction.

\paragraph{Retain candidates that can supply an omitted condition.}
In this same case, demanding an operation match from the initial public-code
localization excludes source13590, which FAISS ranks first. Keeping the
similarity candidate lets the graph return its input relation and construct
the joint program above. This motivates the division in Figure~\ref{fig:method}:
FAISS proposes sources; graph relations support their adaptation to the current
operation. The usefulness of a candidate is established by what its condition
adds to the repair.

\paragraph{Compose roles to expose a broader requirement.}
The timezone relation provides another example. A fixed adapter varies the
historical witness's three zones across database, ambient, and destination
roles and shifts the input by 182 days. Of 72 combinations, the historical
patch improves 20, preserves 20, and leaves 32 incorrect. Applying the same
family to the four timezone content interventions shows that Requirement and
Both pass all 72. Implementation passes the 40 source-supported combinations
but fails the remaining 32, including 16 passed without memory.
Role composition exposes how the current source-timezone requirement interacts
with the historical destination requirement. A complete repair can therefore
satisfy combinations beyond those corrected by the historical implementation.

\paragraph{Design implication.}
A useful memory communicates three things together: the behavior to achieve,
the input relation under which it matters, and an observation that can guide
an edit. A concise sentence sometimes supplies all the agent needs. When
adaptation loses a condition, the graph reconstructs it as an executable input;
feedback then turns the remaining violation into a concrete repair objective.
This progression explains why storing more related text alone can leave the
same bug unresolved, and why preserving a small but decisive relation can
improve the resulting implementation.

\section{Related work}
Graph memory supports associative retrieval through links between experiences
and concepts, as in HippoRAG \citep{hipporag2024}; ExpeL extracts reusable
insights from success and failure \citep{expel2024}. MemOp optimizes memory
writing from downstream success, localization, and efficiency
\citep{memop2026}, while ExpGraph learns retrieval from task scores with and
without experience \citep{expgraph2026}. Our requirement-level interventions
identify what useful memory contributes to the implementation, including
behaviors that differ between repairs with the same official target score.

ExpeRepair generates reproduction and boundary tests from historical
demonstrations \citep{experepair2026}; RETester transforms historical bug
templates while preserving the relevant operation \citep{retester2025}.
MIRA separates SQL corrections into reusable requirements and uses execution
to guide adaptation \citep{mira2026}. TRACE compiles user corrections into rules
and runtime checks \citep{trace2026}. ContextGraph connects the historical
input relation to the current operation, allowing a joint condition to expose
an omission that replaying either example separately misses.

\section{Conclusion}
ContextGraph treats past repairs as reusable requirements for future work.
Historical retrieval results show that experience can improve first-pass
resolution and reduce the retry rounds needed to reach useful solutions.
The executable-memory experiments identify a complementary advantage:
recovering omitted behaviors and preserving them through adaptation.
Combining FAISS candidate selection with graph-based condition construction
provides a concrete path from a relevant past repair to a better current one.
