\begin{abstract}
A coding agent can fix the reported bug and pass official tests while losing
behavior established by an earlier repair. We present ContextGraph, a memory
system that connects past repairs to the requirements a new repair should
preserve. It stores each requirement with its triggering input, operation,
and expected outcome. Retrieved relations help combine historical conditions
with the current workflow, producing executable checks whose failures guide
further edits. Our system evaluations show gains from experience reuse:
ContextGraph resolves 69.2\% of SWE-bench Verified tasks versus 61.8\% without
memory, and reaches 25 resolutions on Related-Lite99 in two passes versus
three without memory. Development experiments explain how memory changes
repair behavior. Historical requirements recover omitted query strings,
uniqueness constraints, and timezone handling; a composed check exposes a
failure that separate current and historical examples both miss. Execution
feedback also corrects a timezone repair left unchanged by further issue-based
review. These
findings suggest a useful form of agent memory: retain the conditions behind
past fixes so that agents can test what a new repair must continue to do.
\end{abstract}

\section{Introduction}
Coding agents repeatedly encounter related bugs, yet a new issue describes
only part of what a complete repair should accomplish. Earlier fixes record
argument precedence, constructor conventions, and neighboring behavior that
must continue to work. Experience can supply requirements that the next
issue leaves implicit.

Consider an administrative redirect that loses a deployment prefix. An agent
can restore the prefix yet discard query parameters when appending a slash.
An earlier fix of the same API supplies the missing requirement: retain the
query string. In our comparison, both repairs pass official verification,
but only the repair using history preserves both behaviors. The earlier
repair helps by telling the agent what else the code must do.

Reusing repair experience raises three challenges.
\paragraph{Losing the triggering condition.}
A summary can retain the requirement yet lose the input relation that makes
it relevant. An agent may follow advice about constraint deletion but test
different columns from those that caused the bug.
\paragraph{Missing an interaction between conditions.}
A current query and a historical named-tuple example may each pass, while
their combination fails. Replaying the examples separately leaves this
interaction unchecked.
\paragraph{Leaving a known requirement unimplemented.}
An agent may understand the requirement yet leave the relevant code unchanged
or revise the wrong branch. Repeating the requirement need not resolve the
remaining failure.

ContextGraph addresses these challenges through three contributions:
\begin{enumerate}
\item \textbf{Requirement memory that preserves triggering conditions.}
We link each requirement to its executable input, operation, and expected
outcome (Section~\ref{sec:store}). The content experiments show how lost
column and constructor relations lead to incomplete repairs, even with a
relevant requirement (Section~\ref{sec:content}).
\item \textbf{Condition composition that checks interactions.}
We use these relations to bring a historical trigger into the current
operation (Section~\ref{sec:compose}). The composition experiments expose a
failure missed by separate examples and show how joint checks help recover
the omitted behavior (Section~\ref{sec:composition-results}).
\item \textbf{Execution feedback that guides requirement-based repair.}
We supply the checks and their failures to guide the next edit
(Section~\ref{sec:feedback}). Refinement experiments recover constraint and
timezone behavior left unresolved by further textual review
(Section~\ref{sec:feedback-results}).
\end{enumerate}
System comparisons additionally measure the benefit of experience reuse
across repair tasks, backbones, and retry budgets (Figure~\ref{fig:results-overview}).

\section{Background and motivation}
\label{sec:motivation}
\paragraph{What should an agent remember?}
Reflexion stores feedback as reflection for later attempts \citep{reflexion2023}.
ExpeL distills reusable insights from trajectories \citep{expel2024};
ReasoningBank learns reasoning memories from successes and failures
\citep{reasoningbank2026}; ACE maintains playbooks through generation,
reflection, and incremental curation \citep{ace2026}. For software repair,
we focus on the behavior learned from a past fix and the conditions under
which that behavior matters.

\paragraph{Values alone do not describe a condition.}
Named tuples and ordinary tuple subclasses can hold identical values but
require different constructor calls. Replacing one by the other in an
example changes what the example tests. Likewise, a timezone value means
something different when it is the database timezone or an explicitly
requested destination. Memory must preserve these roles as well as the values.

\paragraph{Two passing examples can hide a failing combination.}
On a Django repair, a query using a lazy User object passes, and a historical
named-tuple range query also passes. Combining the named-tuple range with the
lazy User in the current query fails. This observation motivates condition
composition: carry the old trigger into the operation being repaired
(Figure~\ref{fig:concept}).

\section{ContextGraph: memory as executable requirements}
\label{sec:method}
\subsection{Requirement memory: preserve triggering conditions}\label{sec:store}
To retain what triggers a requirement, we represent a historical repair with
original and repaired versions $V^{-},V^{+}$ as
\begin{equation}
 m=(r,W,E^{-},E^{+}),\qquad W=(I,A,O),
 \label{eq:witness}
\end{equation}
where $r$ states the requirement, $I$ constructs its triggering input, $A$
performs the operation, and $O$ observes the expected outcome. We call $W$
a witness: an executable example that fails before the historical fix and
passes afterward. $E^{-}$ and $E^{+}$ record these executions.

A source writer reads the historical issue, patch, and relevant code to
propose the requirement and witness. Execution and source review check that
the example exercises the intended behavior. The graph links the repair to
its requirement, program, executions, and input roles. For a range query,
these roles identify the constructor and its two endpoints; for a timezone
conversion, they distinguish the stored instant, active timezone, and destination.
This gives the next agent both an explanation and a concrete way to test it.

\caption{ContextGraph connects source experience to a new repair.
(A) A source writer builds a requirement and witness, checked before and

\paragraph{Retrieve the requirement together with its context.}
The implemented retrieval path uses Qwen3-Embedding-8B and FAISS to select
three distinct witnessed sources from the same repository
\citep{qwen3embedding2025}. Graph joins return their requirements, complete
programs, observations, and input relations. Similarity proposes candidates;
the relations explain how to use them. We keep candidates even when their
operations differ from the initially localized function: an adjacent operation
may carry the requirement the current repair needs to preserve.

Retrieval can also use the agent's evolving context. The full-context search
design lets a code agent inspect complete experiences, follow graph relations,
and search again after a failed attempt. It keeps the same requirement and
execution interface (Appendix~\ref{sec:agentic-retrieval}).

\subsection{Condition composition: check interactions}
\label{sec:compose}
Composition takes a current executable program $P_q$, a relevant memory $m$,
and the relations that map their inputs to operation arguments. An adapter
implements the combination for a supported operation. It retains the current
workflow, adds the historical trigger, and returns a check with an expected
outcome. A useful check must reach the operation and observe its behavior;
an import or fixture error instead calls for fixing the check's setup.

For a scalar equality lookup, our range adapter uses the historical
 two-endpoint named tuple $R$:
\begin{equation}
 P_q(x)\longmapsto P_q^{\mathrm{range}}(R(x,x)).
 \label{eq:composition}
\end{equation}
For a normalized non-null value with equivalent equality and point-range
semantics, the expected selection stays the same. The adapter changes the
lookup argument while preserving how $x$ is constructed and used. Thus a
lazy User inside an annotated subquery remains that object in that query;
replacing it with a lazy integer would lose the interaction. An ordinary-tuple
range supplies a neighboring check. Our second adapter varies database,
ambient, and destination timezones to exercise their different roles.

To select applicable requirements, we compare the historical behavior with
the current issue, documentation, tests, and reachable history. Compatible
requirements become checks; explicitly changed or unclear behavior is left
unenforced. An applicable requirement without an adapter is supplied as cited
text. Appendix~\ref{sec:method-contract} gives the decision procedure.

\paragraph{Preparing the current program.}
In the development cases, $P_q$ combines public issue snippets with
researcher-written setup and observations; both adapters are also
researcher-written. The broader evaluation specifies a shared agent step to
construct a reproducer, prepare its environment, and locate the operation.
All methods receive the same prepared program and count its cost in their
budget. \expmark{Automatic preparation, applicability assessment, and their
shared validation remain to be implemented and evaluated.} If preparation
fails, repair continues with ordinary tools and applicable text memory.

\subsection{Execution feedback: guide requirement-based repair}\label{sec:feedback}
To turn a retrieved requirement into an edit, the coding agent receives the
current issue and selected memory, browses the repository, and runs the checks.
When a supplied check
fails, its program and observations show which behavior the patch still misses.
The agent can revise the implementation and rerun the same check. Keeping the
input and expected outcome fixed makes feedback comparable across edits.
Final patches receive official verification and additional behavioral checks.
Those additional evaluation checks are separate from the checks supplied as
repair guidance.

\section{Experiments}
\label{sec:experiments}
\label{sec:recorded-results}
We first measure overall repair success. The next three studies test the
three contributions in order: what requirement memory must preserve
(Section~\ref{sec:content}), what condition composition reveals
(Section~\ref{sec:composition-results}), and how execution feedback changes
the repair (Section~\ref{sec:feedback-results}). We then examine backbones,
retries, and memory-pool size.

\subsection{Setup and evaluation}
\label{sec:setup}
The system comparisons use SWE-bench Verified and SWEContextBench
\citep{swebench2024,swecontext2026}. They evaluate summary or episodic memory;
the development experiments add executable witnesses and condition composition.
Tables state each comparison's backbone, source pool, and attempt setting.
The development cases use DeepSeek V4 Pro at temperature zero, with matched
budgets within each comparison. Detailed task inputs appear in
Appendix~\ref{sec:development-details}.

Official success comes from each benchmark's verifier. For behavioral
analysis, \emph{Joint} checks the current and historical requirements together,
\emph{Preserve} checks neighboring behavior that already worked, and
\emph{Combined} requires official success and both groups on the same patch.
Case tables report the actual checks and attempts; benchmark tables retain
their completed and planned task counts.
VibeMemBench likewise evaluates coding-agent memory through executable
repository outcomes \citep{vibemembench2026}. Cost measurements include memory
construction, retrieval, check execution, and unsuccessful repair attempts.

\expmark{The additional evaluation compares seven methods on Verified150,
Related-Lite99, LoLBench100, and DeepSWE113, and measures behavior on an
independently annotated held-out sample. These results remain pending in
Appendix~\ref{sec:additional-evaluation}; the red tables collect the work to complete.}

\subsection{Repair effectiveness}
\label{sec:benchmark}
\label{sec:recorded-effectiveness}
With GPT-5.4 and mini-SWE-agent, ContextGraph resolves 346/500 tasks versus
309/500 without memory, a gain of 7.4 percentage points
(Table~\ref{tab:verified500}). It resolves 19 more tasks than FAISS and 26 more
than Agent KB \citep{agentkb2025}.
\textbf{Finding:} experience reuse improves repair success in this comparison.
The next three sections examine what makes that experience useful.

The input's role also matters. On Django12663, both retrieved packets contain
the relevant named-tuple source, yet both initial repairs miss its behavior.
A revision using the historical constructor distinction preserves named tuples
and ordinary subclasses; a revision expanding all non-builtin sequences into
positional arguments breaks the latter (Appendix Figure~\ref{fig:memory-content-scope}).
Requiring an exact operation match also discards this useful source despite
its first-place FAISS rank; relations guide adaptation after source selection.
\textbf{Finding:} a relevant requirement can still lead to an incomplete
repair when its triggering relation is lost. Shared columns and constructor
arguments are decisive in these cases; more implementation text does not
consistently produce a more complete repair.

\subsection{Execution feedback: how does it change the repair?}
\label{sec:feedback-results}
We test whether execution feedback helps implement a known requirement
(Section~\ref{sec:feedback}). Two fresh agents revisit the same failed
constraint repair with the same requirement. Requirement-only review fixes
the primary-key case but misses the ordinary unique-field case. Adding the
source check and its actual failures leads to name disambiguation that fixes
both. On the timezone task, further issue-based review leaves the completed
patch unchanged; the historical check and failure lead to a revision that
honors the destination timezone.

Feedback also helps use a composed condition. Of four fresh refinements of
the Django12663 candidate, history alone passes all seven measured conditions
in one of two attempts; the joint program and its failure do so in two of two.
All four pass official verification. For the simpler redirect task, a sentence
stating the requirement already yields the same correct implementation as
requirement-plus-feedback.
\textbf{Finding:} execution feedback makes a missed condition actionable when
further textual review leaves it unresolved; a clear requirement can suffice
when the agent readily maps it to the right code.

\section{Discussion and related work}
\paragraph{Learning from repair experience.}
SWE-Exp distills successful and failed repair trajectories into reusable
knowledge \citep{sweexp2025}. ExpeRepair combines concrete demonstrations
with reflective insights \citep{experepair2026}; MemGovern organizes GitHub
history into experience cards that agents search and browse
\citep{memgovern2026}. STAIR abstracts trajectories into repair plans at
multiple levels \citep{stair2026}. These approaches provide ways to reuse
what earlier repairs have taught an agent. MemOp optimizes memory through
its effect on downstream tasks, while ExpGraph learns retrieval over linked
experiences \citep{memop2026,expgraph2026}. Recent AdaRepair-Mem also selects
experience according to repository coverage, quality, and repair stage
\citep{adarepairmem2026}. ContextGraph focuses on carrying a historical
requirement and its triggering conditions into the operation being repaired.

\paragraph{Organizing and managing memory.}
MemGPT manages information across context and external storage
\citep{memgpt2023}; SWE-MeM learns when and how to compress the history of a
long coding task \citep{swemem2026}. A-MEM dynamically links and updates
memory notes, while Zep represents facts and their temporal relationships
\citep{amem2025,zep2025}. HippoRAG uses graph connections for associative
retrieval \citep{hipporag2024}. These designs explain how information can
remain available and connected as an agent works. ContextGraph uses input
and operation relations to make retrieved repair experience executable.

\paragraph{Turning experience into checks.}
RETester adapts historical bug reports into tests for refactoring engines
\citep{retester2025}. MIRA separates reusable requirements from SQL corrections,
and TRACE compiles user corrections into runtime checks
\citep{mira2026,trace2026}. Our development cases motivate a further step:
combine the historical trigger with the current workflow, since each example
can pass separately while their combination fails. Retaining the trigger
and its expected outcome gives the agent a concrete repair objective.
The current adapters cover two Django operation families; the additional
evaluation examines broader coverage and independently checked behavior.

\section{Conclusion}
ContextGraph turns past repairs into requirements that a coding agent can
apply and test. It preserves triggering inputs with expected behavior,
composes those conditions with the current operation, and uses execution
failures to guide further edits. System comparisons show higher repair
success and earlier resolution under retries. Development experiments show
what these design choices contribute: retaining a decisive trigger, exposing
an interaction missed by separate examples, and turning a remaining violation
into a concrete next edit. Together, these ideas let an agent use past repairs
as concrete requirements for its current task.
