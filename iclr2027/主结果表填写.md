## 每格怎么填

- 主表一律填解决率（%），例如 `30.0`；单位在表头或表注中统一说明，不在单元格内附解决数。
- 多次独立完整运行填写平均解决率，并在表注说明重复次数；不写标准差。原始逐题结果单独保留，不从均值反推解决数。
- 尚未完成：交付 `resolved、assessed、planned` 三个计数，主表暂标“进行中”。基础设施故障单独记为未评估；不将已评估子集的成功率当成整套最终结果。
- 每个任务一次修复尝试；pass@3、best-of-two 和继续重试的成绩放重试表。

解决率、相对 No memory / FAISS Flat 的百分点增益、配对置信区间由逐题结果计算，你不需要手工填。原论文的主比较表仍要求同时保留 assessed/planned，以便说明是否完整。

## 运行前统一一次的设置

| 字段 | 需要确定的内容 |
|---|---|
| 模型与 agent | 确切模型版本、agent 版本；同一基准的各方法保持一致 |
| 任务集合 | 四份固定 manifest：Verified150、Related-Lite99、LoLBench100、DeepSWE113 |
| 尝试与预算 | 首次尝试；同一基准统一调用、token、时间或费用上限，记录实际配置 |
| 历史输入 | 同一允许使用的历史来源；各方法按自身机制建库，保存实现版本和参数 |
| Flat 与 ContextGraph | 沿用现有方案：相同 top-3 source IDs，比较信息表示与使用方式 |
| 评测 | 每个基准使用对应的官方 verifier，保留逐题输出 |

当前表格并没有把主比较的具体模型和预算值填写完整；不能从旧 Verified500 或 Related-Lite99 表推定这些设置。

## 交付数据的最小格式

每次运行交一份 CSV，列为：

```text
benchmark,method,run_id,task_id,status,resolved,verdict_path
```

`status` 为 `assessed`、`unassessed` 或 `unsubmitted`；仅 assessed 填 resolved=0/1，其他留空。另附一份运行配置，记录上表设置。由这些逐题数据生成所有主表数值。

## 填写顺序

先收齐 No memory、FAISS Flat、ContextGraph 在四个基准上的 12 格；再补现有四种外部方法的 16 格。Supermemory 是建议追加的 4 格。这个顺序用于结果整理与实验排期，不授权启动或重启任何运行。
